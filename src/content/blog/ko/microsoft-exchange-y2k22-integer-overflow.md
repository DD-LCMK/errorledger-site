2022년 1월 1일이 되었습니다. 전 세계 기업의 IT 부서는 새해를 맞이하며 핵심 인프라가 문제없이 작동할 것이라 굳게 믿고 있었습니다. 22년 전 악명 높았던 Y2K 전환과 달리, 2022년으로의 전환은 날짜 구문 분석 오류를 일으킬 것이라 예상되지 않았습니다. 그러나 협정 세계시(UTC)로 자정이 지나자마자 시스템 관리자들은 조직 내 통신이 갑작스럽고 치명적으로 중단되는 것을 목격하기 시작했습니다. 전 세계적으로 Microsoft Exchange Server 인프라가 수발신 이메일 전송을 돌연 중단한 것입니다.

근본 원인은 정교한 사이버 공격도, 데이터 센터의 대규모 하드웨어 장애도, 복잡한 분산 시스템의 경쟁 상태(Race Condition)도 아니었습니다. 안티 멀웨어 스캔 엔진 깊숙한 곳에 숨겨진 단 하나의 조용한 수학적 필연성, 즉 32비트 부호 있는 정수가 최대 용량에 도달했기 때문이었습니다. `2201010001`이라는 날짜를 `2,147,483,647`로 제한된 데이터 유형으로 구문 분석하려 시도함으로써, 엔진은 치명적인 예외를 발생시켰고, 결과적으로 전 세계의 온프레미스 이메일 인프라가 마비되었습니다.

## Microsoft Exchange Server란 무엇이었는가?
Microsoft Exchange Server는 세계에서 가장 널리 배포된 기업용 이메일 및 캘린더 플랫폼 중 하나입니다. 많은 조직이 Microsoft의 클라우드 기반 Office 365(현재 Microsoft 365)로 마이그레이션했지만, 수많은 기업, 정부 기관 및 규제 대상 산업은 데이터 주권, 규정 준수 및 제어를 위해 Exchange Server 2016 및 2019의 온프레미스 배포를 유지하고 있었습니다.

이러한 로컬 네트워크를 악성 첨부 파일과 스팸으로부터 보호하기 위해 Exchange Server는 FIP-FS(Filtering Management Service) 엔진이라는 통합 검사 구성 요소를 사용했습니다. 이 엔진은 전송 파이프라인에 위치했습니다. 조직에 들어오거나 나가는 모든 이메일은 FIP-FS로 전달되었습니다. 엔진은 Microsoft에서 동적으로 서명 업데이트를 다운로드하고 표준화된 숫자 스키마를 사용하여 해당 서명의 버전을 확인했습니다. 이메일이 스캔을 통과하면 배달되었습니다. 그러나 스캔 엔진이 실패하면 Exchange 전송 서비스는 잠재적으로 위험한 페이로드가 네트워크로 전달되는 것을 거부하고 방어적으로 이메일을 대기열에 넣었습니다.

> **증거가 입증하는 것:**
> - Exchange Server 2016 및 2019는 2022년 1월 1일 00:00 UTC에 메시지 처리를 중단했습니다.
> - 근본 원인은 날짜 문자열을 32비트 정수로 구문 분석할 때 발생한 `System.FormatException`으로 인한 `Microsoft.Filtering.FipsFS` 프로세스의 `Unhandled Exception`이었습니다.
> - Microsoft는 서명 업데이트 버전 형식을 변경하는 것과 관련된 해결 방법을 공식적으로 문서화했습니다.
> - 수백만 개의 메시지가 전송 대기열에 멈춰 시스템 관리자가 수동으로 개입해야 했습니다.

> **증거가 입증하지 않는 것 (What the evidence does NOT establish):**
> - 이번 다운타임을 유발한 표적 사이버 공격이나 악의적인 익스플로잇에 대한 증거는 없습니다.
> - 데이터가 영구적으로 손실되었다는 증거는 없습니다. 이메일은 대기열에 들어갔을 뿐 삭제되지 않았습니다.
> - 클라우드 기반 Exchange Online 고객이 영향을 받았다는 증거는 없습니다. 결함은 온프레미스 FIP-FS 엔진에 국한되었습니다.

## 제1막: 자정을 알리는 시계

2022년으로의 전환은 완전히 일상적인 과정이어야 했습니다. 현대의 소프트웨어 시스템은 일찌감치 64비트 아키텍처와 훨씬 먼 미래의 타임스탬프(예: 2038년의 유닉스 에포크 한계)를 처리하도록 설계된 강력한 날짜 시간 라이브러리를 표준으로 채택했습니다.

2022년 1월 1일 자정(UTC), Microsoft 서명 생성 서버는 새해로 넘어갔습니다. 표준 운영 절차에 따라 FIP-FS 엔진을 위한 최신 안티 멀웨어 및 안티 스팸 정의를 게시했습니다. Microsoft가 이러한 정의에 사용한 버전 스키마는 `YYMMDDXXXX`로 구성되었으며, 여기서 `YY`는 두 자리 연도, `MM`은 월, `DD`는 일, 그리고 `XXXX`는 일중 업데이트를 위한 네 자리 시퀀스 번호를 나타냅니다.

2021년의 마지막 업데이트의 경우 버전 번호는 `211231XXXX`(예: `2112310009`)로 2021년 12월 31일을 나타냈습니다. 이 숫자는 약 21억 1천만으로 평가되었습니다.

2022년의 첫 번째 업데이트가 게시되었을 때 서명 문자열은 `"2201010001"`이 되었습니다.

전 세계의 온프레미스 Exchange Server는 이 새로운 서명 파일을 자동으로 다운로드했습니다. 백그라운드 Windows 서비스(`fms.exe` 및 관련 프로세스)로 작동하는 FIP-FS 서비스는 다운로드한 업데이트가 이전에 설치된 버전보다 최신인지 확인하기 위해 이 문자열을 내부 메모리 구조로 구문 분석하려고 시도했습니다.

그리고 즉각적으로 실패했습니다.

## 제2막: 32비트 한계의 아키텍처

취약점은 버전 확인 논리를 처음 설계한 소프트웨어 엔지니어가 사용한 데이터 유형의 선택에 전적으로 존재했습니다. Exchange 관리 인프라의 많은 부분을 뒷받침하는 C# 및 .NET 프레임워크에서 `Int32`(부호 있는 32비트 정수)는 `-2,147,483,648`에서 `2,147,483,647`까지의 값을 나타낼 수 있습니다.

십 년 이상 동안 `YYMMDDXXXX` 스키마는 이 상한선 아래에 안전하게 상주했습니다. 2019년에는 약 19억, 2020년에는 약 20억의 값을 생성했습니다. 2021년에는 그 값이 21억 1천만으로 한계에 아슬아슬하게 근접했지만 여전히 엄격하게 유효한 범위 내에 있었습니다.

```text
다이어그램: [DOCUMENTED] FIP-FS 버전 파싱 아키텍처
┌────────────────────────────┐      ┌─────────────────────────────┐
│ 서명 업데이트 서버         │      │ Exchange Server (온프레미스)│
│ 생성: "2201010001"         │───▶  │ FIP-FS 엔진                 │
└────────────────────────────┘      └──────┬──────────────────────┘
                                           │
                                           ▼
                            [DOCUMENTED] 정수 파싱
                            long.Parse("2201010001") -> Int32?
                            잠깐, 변수가 Int32입니다!
                                           │
                                           ▼
                            [RECONSTRUCTED] 예외 발생
                            System.FormatException / Overflow
                                           │
                                           ▼
                            [DOCUMENTED] 전송 파이프라인 중단
                            메시지가 대기열에 고립됨
```

`Int32.Parse("2201010001")` 또는 동등한 변환 함수가 호출되었을 때, `2,201,010,001`이라는 값은 `2,147,483,647`을 약 5,350만 초과했습니다. 런타임 환경은 당연히 예외를 발생시켰습니다. 이러한 구문 분석은 FIP-FS 엔진의 초기화 또는 업데이트 유효성 검사 시퀀스 중에 발생했기 때문에 서비스가 중단되었습니다. 보안을 위해 안전하게 닫히도록 설계된 Exchange 전송 파이프라인은 먼저 스캔하지 않고는 메일을 라우팅하기를 거부했습니다. 그 결과 거대한 백로그가 발생했습니다.

이 사건은 64비트 부동 소수점 숫자가 안전하지 않게 16비트 정수로 변환되어 5억 달러 규모의 우주선이 파괴된 [아리안 5 501편 정수 오버플로](/blog/ariane-5-flight-501-integer-overflow)와 같은 다른 유명한 숫자 경계 실패를 강력하게 연상시킵니다. Exchange 버그는 폭발을 일으키지는 않았지만, 수천 개의 기업에서 글로벌 통신을 효과적으로 마비시켰습니다.

## 제3막: 대기열의 붕괴와 복구

다양한 시간대에서 1월 1일 아침이 밝아오자 관리자들은 Exchange 전송 대기열이 기하급수적으로 쌓이고 있다는 모니터링 알림을 받고 깨어났습니다. 애플리케이션 이벤트 로그는 FIP-FS 프로세스와 스캔 프로세스에 관련된 "Error: 0x80004005"를 명시적으로 인용하는 오류 5300 및 오류 1106으로 가득 찼습니다.

시스템이 닫힌 상태로 실패했기 때문에 조직은 이메일을 보내거나 받을 수 없다는 중요한 운영상의 딜레마에 직면했습니다. [Fastly 2021 글로벌 장애](/blog/fastly-2021-global-outage)와 마찬가지로, 단일 로직 결함이 신속하게 글로벌 서비스 거부(Denial of Service)로 이어졌지만, 이 경우는 중앙 집중식 CDN이 아닌 고객 데이터 센터 내부에 완전히 국한되었습니다.

Microsoft는 커뮤니티에서 신속하게 "Y2K22 버그"로 명명한 이 문제를 재빨리 인정했습니다.

초기 문제 해결 방식은 다소 원초적이었습니다. Microsoft는 관리자가 FIP-FS 안티 멀웨어 검색 엔진을 완전히 우회하도록 요구하는 PowerShell 스크립트(`Reset-ScanEngineVersion.ps1`)와 수동 지침을 제공했습니다. `Set-MalwareFilteringServer -BypassFiltering $True`를 실행하고 전송 서비스를 다시 시작함으로써 악성 코드 검사 없이 이메일이 자유롭게 흐르도록 허용했습니다. 이는 일시적으로 통신을 복구했지만 조직의 방어 태세를 저하시켰고, 악성 페이로드를 잡기 위해 엔드포인트 보호 또는 업스트림 서드파티 메일 게이트웨이에 전적으로 의존하게 만들었습니다.

영구적인 해결책에는 약간 특이하지만 우아한 구조적 대안이 필요했습니다. 데이터 유형을 64비트 정수(`Int64`)로 확장하기 위해 대규모 바이너리 패치를 배포하는 대신 Microsoft는 서명 생성 서버를 변경했습니다. 그들은 서명 버전을 리터럴 역년에서 분리했습니다. 2022년의 새로운 서명 버전은 2021년의 가상의 "13번째 달"로 롤백되었습니다.

2022년 서명을 `2112330001`로 시작함으로써 숫자 값은 21억 4천만 임계값 아래에 안전하게 유지되면서도 여전히 2021년 12월 31일 서명보다 수학적으로 더 크다는 것을(따라서 더 최신이라는 것을) 보장할 수 있었습니다.

## 시스템 예방 플레이북

Y2K22 Exchange 버그는 임의적인 레거시 아키텍처 결정이 어떻게 수십 년 후에 파괴적으로 표면화될 수 있는지 명확하게 보여줍니다. 유사한 경계 실패를 방지하려면 구체적인 엔지니어링 개입이 필요합니다.

### 1. 데이터 유형 경계 단언(Assertions)
날짜나 타임스탬프를 기반으로 하는 숫자 식별자가 기존 한도 내에 계속 유지될 것이라고 암묵적으로 가정하지 마십시오. 형식에 `YYMMDDXXXX`를 사용하는 경우 명시적인 수학적 단위 테스트는 지속적 통합(CI) 중 할당된 메모리 유형과 비교하여 이론상 최대값(예: `9912319999`)을 검증해야 합니다.

### 2. 보안 파이프라인의 우아한 성능 저하(Graceful Degradation)
비핵심 또는 보조 보안 서비스가 중단될 때 시스템은 지능적으로 대처해야 합니다. 보안 검사에 실패하면 악성코드가 진입하는 것을 막을 수 있지만, 업데이트 모듈의 구문 분석 오류로 인해 전체 검색 엔진이 중단되어서는 안 됩니다. 시스템은 완전히 중단되지 않고 마지막으로 알려진 양호한 서명 상태로 되돌아가야 합니다.

### 3. 가상의 날짜 오프셋
데이터 유형을 확장하기 위해 레거시 바이너리를 쉽게 패치할 수 없는 경우, 오프셋 연산(접두사를 `211233`으로 고정하는 등)을 사용하는 것은 고도로 효과적이고 검증된 완화 패턴입니다. 이는 이전 버전과의 호환성을 보장하면서도 숫자 오버플로를 방지합니다.

## 아키비스트의 판결

> Microsoft Exchange Y2K22 버그는 기술 부채(Technical Debt)가 단순히 지저분한 코드가 아니라 째깍거리는 수학적 시한폭탄이라는 심오한 사실을 상기시켜 줍니다. 날짜 문자열을 32비트 부호 있는 정수로 매핑하기로 한 결정은 처음 시작될 당시에는 완전히 합리적이었습니다. 2000년대 초반에 2022년은 기능적으로 무한한 미래처럼 느껴졌을 것입니다.

> 이 실패는 복잡한 네트워크 파티션이나 다중 스레딩 경쟁 상태가 아니었습니다. 이것은 소프트웨어 물리학이 자신을 주장하는 가장 순수한 형태였습니다. 즉, 컨테이너는 오직 그것이 담도록 설계된 것만을 담을 수 있다는 사실입니다. `2,201,010,001`이라는 값이 `2,147,483,647`로 엄격하게 제한된 컨테이너와 만났을 때, 애플리케이션은 붕괴할 수밖에 없었습니다.

> 이 사건의 가장 흥미로운 측면은 해결책이었습니다. 파이프를 넓히기 위해 배관을 뜯어내는 대신 Microsoft는 32비트 세계관의 엄격한 제약을 충족시키기 위해 2021년 12월의 가상의 33일을 발명하여 물의 형태 자체를 바꿨습니다. 이것은 결함이 있는 아키텍처를 수정하는 가장 빠른 방법이 때로는 창조적으로 거짓말을 하는 것임을 보여주는 실용적인 사고 대응의 훌륭한 사례입니다.

## 자주 묻는 질문 (FAQ)

### Y2K22 Microsoft Exchange 버그의 원인은 무엇이었나요?
이 버그는 정수 오버플로로 인해 발생했습니다. FIP-FS 안티 멀웨어 엔진은 연도가 2022년으로 바뀔 때 32비트 부호 있는 정수 한도인 2,147,483,647을 초과하는 버전 지정 체계(YYMMDDXXXX)를 사용했습니다.

### Microsoft는 이 문제를 어떻게 해결했나요?
Microsoft는 맬웨어 검사를 우회하는 임시 해결 스크립트를 제공했으며, 이후 서명 버전이 32비트 한도에 맞도록 (2021년의 가상의 날짜로 작동하는) '211233'으로 시작하도록 변경하는 업데이트를 출시했습니다.

### 어떤 버전의 Exchange가 영향을 받았나요?
FIP-FS 안티 멀웨어 검색 엔진을 활발하게 사용하는 Microsoft Exchange Server 2016 및 2019 온프레미스 설치 환경이 영향을 받았습니다.

### 이 버그가 보안 위험을 초래했나요?
네, 즉각적인 해결 방법에는 FIP-FS 안티 멀웨어 스캔 엔진을 비활성화하는 것이 포함되었으므로 영구적인 수정 사항이 배포될 때까지 조직은 악성 첨부 파일에 일시적으로 노출되었습니다.
