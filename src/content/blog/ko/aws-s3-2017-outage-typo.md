## 경영진 요약 (Executive Summary)

2017년 2월 28일, Amazon Web Services(AWS) 내부의 일상적인 디버깅 세션은 4시간 이상 인터넷의 상당 부분에 장애를 발생시킨 연쇄적인 실패를 촉발했습니다. US-EAST-1 리전의 S3 결제(billing) 하위 시스템에서 소수의 서버를 제거하려던 승인된 엔지니어가 기존 플레이북 명령어에 잘못된 입력을 범했습니다. (이 사건은 흔히 오타로 묘사됩니다.) 해당 운영 도구는 잘못된 입력으로 인해 의도했던 것보다 훨씬 더 큰 서버 세트를 제거하도록 허용했으며, 여기에는 인덱스 및 배치 하위 시스템을 강제로 재시작하게 만드는 충분한 용량이 포함되어 있었습니다. 수년 동안 완전히 재부팅된 적이 없는 이 핵심 시스템들의 전체 재시작은 장기적인 복구 기간을 초래했으며, 이로 인해 수많은 하류 애플리케이션, AWS 서비스 및 고객 워크로드에 장애가 발생했습니다.

## Amazon S3 US-EAST-1은 무엇이었나? (What Was Amazon S3 US-EAST-1?)

Amazon Simple Storage Service(S3)는 전 세계 개발자들이 데이터를 저장하고 검색하는 데 사용하는 기본적인 객체 스토리지 서비스입니다. 이 사건은 AWS의 북버지니아(US-EAST-1) 리전에서 발생했습니다. S3 내에서 몇 가지 거대한 분산 하위 시스템이 협력하여 작동합니다. 인덱스 하위 시스템은 메타데이터와 모든 객체의 물리적 위치를 관리하며, 배치 하위 시스템은 새 데이터가 기록되어야 할 위치를 결정합니다. 기본 스토리지 인프라로서의 S3의 역할 때문에, US-EAST-1에서 해당 API를 사용할 수 없게 되었을 때 여러 AWS 서비스가 영향을 받았습니다. AWS는 영향을 받은 서비스 중 S3 콘솔, 새 EC2 인스턴스 시작, S3 스냅샷의 데이터가 필요한 EBS 볼륨, 그리고 AWS Lambda를 지목했습니다.

## 제1막: 이상 징후의 순간 (Act I: The Moment of Anomaly)

이 사건은 경보가 아니라 일상적인 최적화 노력에서 시작되었습니다. 2017년 2월 28일 아침, S3 팀은 US-EAST-1 결제 하위 시스템에서 예상보다 높은 지연 시간을 발견했습니다. 최적의 성능을 복원하기 위해 엔지니어들은 결제 서버 중 일부를 제거하기로 결정했습니다.

태평양 표준시 오전 9시 37분(미동부 표준시 오후 12시 37분), 승인된 엔지니어는 터미널을 열고 대상 서버를 오프라인으로 전환하기 위해 확립된 플레이북 명령어를 실행했습니다. [공식 AWS 사후 보고서(Postmortem)에 따르면](https://aws.amazon.com/message/41926/): *"안타깝게도 명령어 입력 값 중 하나가 잘못 입력되어 의도한 것보다 더 큰 서버 집합이 제거되었습니다."*

터미널은 입력을 수락했습니다. 해당 운영 도구는 잘못된 입력으로 인해 의도했던 것보다 훨씬 더 큰 서버 세트를 제거하도록 허용했으며, 여기에는 관련 인덱스 및 배치 하위 시스템의 전체 재부팅을 강제할 만큼의 용량이 포함되어 있었습니다.

## 제2막: 덫의 구조 (Act II: The Architecture of the Trap)

시스템 엔지니어링 관점에서 볼 때, 더 중요한 실패 원인은 잘못된 입력 그 자체보다 운영 도구 내에 충분한 용량 제거 안전장치(누락된 **경계 제약(Boundary Constraint)**)가 부재했다는 점이었습니다. 결제 작업을 위해 대상으로 지정된 서버는 인덱스와 배치라는 두 가지 다른 S3 하위 시스템도 지원했습니다.

| :--- | :--- | :--- | :--- | :--- |
| **대상 범위** | 소규모 결제 용량 제거 | 훨씬 더 큰 서버 세트 제거됨 | [DOCUMENTED] | 잘못된 명령어 입력 |
| **용량 상태** | 예상되는 안전한 용량 감소 | 전체 재시작이 필요할 정도로 감소된 인덱스/배치 용량 | [DOCUMENTED] | 과도한 용량 제거 |
| **복구 상태** | 일상적 서비스 운영 | 하위 시스템 전체 재시작 필요 | [DOCUMENTED] | 심각한 용량 손실 |

## 제3막: 파열의 순서 (Act III: The Sequence of the Fracture)

갑작스러운 용량 손실은 인덱스와 배치 하위 시스템 모두를 즉각적이고 예상치 못한 전체 재시작(full restart) 상태로 몰아넣었습니다.

### 텔레메트리 타임라인 테이블 (Telemetry Timeline Table)

| 시간 (PST) | 이벤트 | 인식 상태 (Epistemic State) | 결과 (Consequence) |
| :--- | :--- | :--- | :--- |
| **오전 9:37** | 엔지니어가 잘못된 입력으로 확립된 플레이북 명령어를 실행함. | `FACT` | 의도한 것보다 많은 용량이 제거됨. |
| **용량 제거 이후** | 인덱스 및 배치 용량이 부족해져 두 가지 모두 재시작해야 함. | `FACT` | S3 요청 처리를 이용할 수 없게 됨. US-EAST-1의 S3 API 요청이 실패하기 시작하여 광범위한 하류 서비스 중단을 야기함. |
| **오후 12:26** | 인덱스가 GET, LIST 및 DELETE 처리를 시작함. | `FACT` | 부분적인 S3 복구가 시작됨. |
| **오후 1:18** | 인덱스가 완전히 복구됨. | `FACT` | GET, LIST 및 DELETE가 정상적으로 작동함. |
| **오후 1:54** | 배치 하위 시스템이 완전히 복구됨. | `FACT` | S3가 정상적으로 작동함. |

복구가 이례적으로 느렸던 이유는 S3가 이전 수년간 엄청난 성장을 경험했기 때문입니다. [AWS는 인정했습니다](https://aws.amazon.com/message/41926/): *"우리는 다년 간 더 큰 리전에서 인덱스 하위 시스템이나 배치 하위 시스템을 완전히 재시작한 적이 없었습니다."* 현실적인 측면에서 볼 때, 이 사건은 한 번도 전체 재시작을 하지 않은 채 다년간 운영된 대규모 하위 시스템을 완전히 재시작하는 것의 어려움을 드러냈습니다. 메타데이터 무결성 점검은 예상보다 훨씬 오래 걸렸습니다.

## 제4막: 인간과 시스템의 확대 (Act IV: The Human & Systemic Escalation)

S3 하위 시스템이 재시작을 위해 분투하는 동안, 장애는 수평적으로 확대되었습니다. AWS 서비스 상태 대시보드의 관리 콘솔은 Amazon S3에 의존성이 있었으며, 이로 인해 사건 발생 시작부터 태평양 표준시 오전 11시 37분까지 AWS가 개별 서비스 상태를 업데이트하지 못했습니다.

### 외부 추정치 테이블 (External Estimation Table)

| 주체 (Entity) | 역할 (Role) | 결과 (Consequences) | 증거 상태 (Evidence Status) |
| :--- | :--- | :--- | :--- |
| **제3자 비즈니스** | 고객 | Cyence는 피해를 입은 S&P 500 기업의 손실을 약 1억 5천만 달러로 추정했으며, 미국 금융 서비스 기업에 대한 별도의 추정치는 약 1억 6천만 달러였습니다. | `EXTERNAL ESTIMATE` |
| **AWS 상태 대시보드** | 통신 계층 | 중대한 장애 기간 동안 업데이트 실패. | `FACT` |

이 장애는 중요한 운영적 의존성(operational dependency)을 드러냈습니다. 서비스 상태를 전달해야 하는 시스템 자체가 장애를 겪고 있는 인프라에 의존하고 있었습니다.

## 기존의 안전장치들이 실패한 이유 (Why the Existing Safeguards Failed)

이 사고는 S3 서비스의 기본적인 용량 장애 모델의 실패라기보다는 운영 도구의 간극을 드러냈습니다. AWS는 시스템이 상당한 용량 장애를 견딜 수 있도록 엔지니어링했지만, 도구는 용량이 너무 빨리 제거되도록 허용했으며 잘못된 입력으로 인해 하위 시스템이 최소 필수 용량 아래로 내려가는 것을 막지 못했습니다.

복구 경로는 두 번째 약점을 드러냈습니다. 인덱스 및 배치 하위 시스템은 수년 동안 AWS의 대규모 리전에서 완전히 재시작된 적이 없었습니다. S3가 상당히 성장함에 따라 재시작 및 메타데이터 무결성 검증 프로세스는 예상보다 훨씬 오래 걸렸습니다.

## 엔지니어링 진화 (Engineering Evolution)

| 기능 (Feature) | 2017년 실패 패턴 (Failure Pattern) | 사고 이후 방어 패턴 (Defensive Pattern) |
| :--- | :--- | :--- |
| **용량 제거** | 과도한 용량 제거 권한 | 느린 용량 제거 + 최소 용량 안전장치 |
| **복구 파티셔닝(Recovery Partitioning)** | 예상보다 긴 재시작이 필요한 대규모 인덱스 하위 시스템 | 추가적인 인덱스 파티셔닝 및 셀 기반 아키텍처 지속 |
| **서비스 상태 대시보드** | SHD 관리가 S3에 의존 | SHD 관리 콘솔이 여러 AWS 리전에서 운영되도록 변경 |
| **하위 시스템 초기화** | 장기간 테스트되지 않은 재시작 경로 | 하위 시스템 복구 테스트 및 개선에 더 큰 중점 |

## 시스템 예방 플레이북: 엔지니어링 권장 사항 (Systems Prevention Playbook: Engineering Recommendations)

이 사고는 고위험 인프라에 구현해야 할 중요한 방어적 격차를 강조합니다:

1. **마찰 방어 (Friction Defenses):** 영향이 큰 운영 명령어는 실행 전에 사전 실행(dry-run) 미리보기, 명시적 확인 또는 독립적인 검증을 제공해야 합니다.
2. **경계 제약 (Boundary Constraints):** 도구는 자동으로 최소 안전 용량을 강제해야 합니다. 운영자는 일반적인 명령 매개변수를 통해 중요한 안전 경계를 우회할 수 없어야 합니다.
3. **종속성 격리 (Dependency Isolation):** 운영 통신 시스템은 모니터링하는 인프라에 장애가 발생할 때 독립적으로 가용성을 유지해야 합니다.

## 아키비스트의 판결 (The Archivist Verdict)

> **아키비스트의 분석:**
> 
> **증거가 입증하는 것:**
> 승인된 엔지니어가 결제 시스템을 디버깅하는 동안 기존 플레이북 명령어에서 오타를 범했습니다. 이 명령어에는 경계 제약이 없었으며 인덱스 및 배치 하위 시스템에서 의도한 것보다 훨씬 많은 서버 용량을 제거했습니다. 이러한 거대한 하위 시스템의 이후 전체 재시작은 몇 시간이 걸려 광범위한 서비스 중단으로 이어졌습니다.
> 
> **증거가 입증하지 않는 것 (What the evidence does NOT establish):**
> 서비스 중단이 사이버 공격, 악의적 의도 또는 외부 공격자에 의해 발생했다는 것. 또한 운영 도구 자체에 조치를 방지하는 필수 안전 장치가 부족했기 때문에 엔지니어가 필수 안전 프로토콜을 우회했음을 입증하지 않습니다.
> 
> 더 깊은 실패의 원인은 단순히 운영자가 실수를 저질렀기 때문이 아닙니다. 진정한 문제는 운영 제어 평면이 최소한의 안전 상태를 강제하지 않고 평범한 입력 오류가 치명적인 시스템 경계를 넘도록 허용했다는 것입니다. 시스템은 운영자가 언젠가는 실수할 것이라는 가정하에 설계되어야 합니다. 기본 경계 제약 조건을 구현하지 못하고 통신 대시보드가 모니터링하는 인프라에 의존하도록 허용함으로써, 운영 도구는 시스템의 복원력 가정을 무너뜨릴 만큼 충분히 큰 용량 제거를 허용했습니다. 진정한 교훈은 시스템의 복잡성이 커짐에 따라 운영 도구도 그에 맞추어 방어적인 마찰력(friction)을 갖추어야 한다는 것입니다. ## 자주 묻는 질문 (FAQ)

### 2017년 AWS S3 서비스 중단의 원인은 무엇입니까?
결제 시스템 지연 문제를 디버깅하던 승인된 엔지니어가 오타가 포함된 명령어를 입력하여 의도한 것보다 훨씬 많은 서버 용량을 실수로 제거했습니다. 이는 S3 인덱스 및 배치 하위 시스템에서 연쇄적인 장애를 촉발했습니다.

### AWS S3 서비스 중단을 해결하는 데 왜 그렇게 오래 걸렸습니까?
장애가 발생한 하위 시스템들은 수년에 걸쳐 엄청나게 성장했으며 US-EAST-1 리전에서는 완전히 재시작된 적이 없었습니다. S3가 실질적으로 성장함에 따라, 재시작과 메타데이터 무결성 검증 프로세스가 예상보다 훨씬 오래 걸렸습니다.

### 2017년 장애 이후 AWS는 변경 사항을 적용했습니까?
네. AWS는 용량 제거 도구에 경계 제약을 추가하여 최소 용량 수준 이하로 서버를 제거하지 못하게 했으며, 서비스 상태 대시보드(Service Health Dashboard)의 관리 콘솔이 여러 AWS 리전에 걸쳐 작동하도록 변경했습니다.

### AWS는 서비스 중단 중에 왜 상태 페이지를 업데이트할 수 없었습니까?
AWS 서비스 상태 대시보드의 관리 콘솔은 Amazon S3에 의존성이 있었으며, 이로 인해 사건 발생 시작부터 태평양 표준시 오전 11시 37분까지 AWS가 개별 서비스 상태를 업데이트하지 못했습니다.

### 2017년 AWS 장애로 인해 영향을 받은 서비스는 무엇입니까?
이 서비스 중단은 US-EAST-1에서 S3에 의존하는 수많은 웹사이트, 애플리케이션, 연결된 디바이스 및 AWS 서비스에 영향을 미쳤습니다. AWS는 특히 영향을 받은 서비스 중 S3 콘솔, 새 EC2 인스턴스 시작, S3 스냅샷의 데이터가 필요한 EBS 볼륨, 그리고 AWS Lambda를 지목했습니다. 동시대의 보도에 따르면 Slack, Quora, Trello 및 기타 주요 플랫폼의 서비스 중단도 문서화되었습니다.

### 사이버 공격이었나요?
아니요. AWS 사후 보고서는 이 사건을 악의적이거나 외부적인 활동의 징후 없이 내부 디버깅 중 잘못된 입력으로 인해 발생한 운영 사고로 설명합니다.
