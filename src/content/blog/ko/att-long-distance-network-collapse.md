1990년 1월 15일, 뉴욕의 한 AT&T 4ESS 교환기에서 발생한 사소한 하드웨어 오류가 일상적인 복구 순서를 촉발했습니다. 교환기는 설계된 대로 복구되었습니다. 문제는 그 다음에 일어난 일이었습니다. 복구 트래픽이 AT&T의 114개 교환기 전체에 존재하는 소프트웨어 결함을 노출시켰고, 인접한 신호 프로세서들이 마비되며 이 장애가 국가 통신망 전체로 전파된 것입니다.

9시간 동안 미국의 최고 통신 네트워크는 프로세서 장애, 초기화 및 복구 트래픽의 연쇄적인 순환에 빠져들었습니다. 이 사건은 수백만 명의 장거리 전화 서비스를 끊어놓았고, 고도로 연결되고 동질적인 시스템에서 장애 복구 메커니즘이 뜻하지 않게 전염병의 매개체 역할을 할 때 시스템이 어떻게 작동하는지를 연구하는 새롭고 시급한 학문 분야를 확립했습니다.

## 4ESS와 CCS7 네트워크란 무엇이었나?

1990년 당시 AT&T 장거리 인프라의 중추는 **4ESS(Number 4 Electronic Switching System)**였습니다. 각각의 4ESS는 초당 수천 통의 전화를 라우팅하도록 설계된 거대하고 신뢰성이 높은 전화 교환기였습니다.

이 교환기들은 ITU 표준 신호 아키텍처인 **공통선 신호 방식 No. 7(CCS7)**을 사용하는 별도의 데이터 네트워크를 통해 서로 통신했습니다. 음성 회선 자체를 통해 신호를 보내(대역 내 신호) 통화를 설정하는 대신, 교환기들은 CCS7 네트워크를 통해 디지털 메시지를 교환했습니다(대역 외 신호). 이를 통해 네트워크는 훨씬 더 빠르게 통화를 라우팅하고, 800번 전화 라우팅을 위해 데이터베이스를 조회하며, 음성 채널을 할당하지 않고도 멀리 떨어진 교환기에게 회선이 통화 중인지 즉시 알릴 수 있었습니다.

이 4ESS에서 신호 인터페이스를 처리하는 핵심 구성 요소는 **Direct Link Node(DLN)**로, CCS7 신호 네트워크와 관련된 상태 정보를 유지하는 역할을 담당하는 프로세서였습니다.

## 12월 중순의 소프트웨어 업데이트

몇 주 동안 이 업데이트된 소프트웨어는 현장에서 장애 유발 시퀀스가 발생하지 않은 채 작동했습니다. 이 업데이트는 기본 CCS7 신호 네트워크에 문제가 발생했을 때 교환기가 백업 신호 네트워크에 더 빨리 액세스할 수 있도록 하여 네트워크 성능을 향상시키기 위한 것이었습니다.

AT&T는 인프라 전반에 걸쳐 엄격한 표준화를 유지했기 때문에, 동일한 취약점을 가진 소프트웨어 업데이트가 114개의 모든 4ESS 교환기에 도입되어 있었습니다.

## 사고 전개 과정

장애는 맨해튼에서 국지적이고 완전히 정상적인 오류로 시작되었습니다.

### 1. 트리거 (The Trigger)
오후 2시 25분경(EST), 뉴욕 4ESS의 트렁크 인터페이스 장비에 내부 하드웨어 문제가 발생했습니다. 이 교환기는 정상적인 오류 복구 절차에 들어가 일시적으로 새 통화 수신을 중단하고 연결된 교환기들에게 통보했습니다.

### 2. 서비스 복귀 (The Return to Service)
뉴욕 교환기가 복구되어 서비스에 복귀했을 때, 통화 처리를 재개하고 연결된 교환기들에게 통화를 설정하기 위한 **초기 주소 메시지(IAM)**를 보냈습니다.

### 3. 취약성 창 (The Vulnerability Window)
복구 중인 뉴욕 교환기로부터 첫 번째 IAM을 수신한 후 연결된 교환기의 DLN은 상태 맵 업데이트를 시작합니다. 이때 1/100초 이내에 도착한 두 번째 IAM이 결함을 촉발시켰습니다.

### 4. 데이터 손상 (The Data Corruption)
소프트웨어 결함으로 인해 수신 측 DLN은 중요한 포인터 초기화를 건너뛰었습니다. 프로세서의 데이터가 손상되었고, 오류 복구 로직이 이 불일치를 감지하여 교환기의 작동을 중단시켰습니다.

### 5. 연쇄 반응 (The Cascade)
영향을 받은 교환기가 다운되자, 해당 교환기는 연결된 피어들에게 자체 복구 관련 신호를 보냈습니다. 이 교환기가 이후 서비스에 복귀했을 때, 이 교환기가 재개한 통화 트래픽은 *자신의* 이웃 교환기들에게서 똑같은 결함을 노출시켜 이들을 다운시켰습니다. 이 장애는 국가 네트워크 전체로 전파되었습니다.

## 재구성된 C 결함

*(분석적 재구성)* 결함이 있는 C 구조의 발표된 재구성에 따르면, 잘못 배치된 `break`가 포인터 초기화 경로를 우회했음을 보여줍니다. 따라서 후속 처리는 초기화되지 않은 포인터를 가지고 작동했으며, 이는 AT&T의 당시 설명에서 서술한 데이터 손상을 일으켰습니다.

결함은 중첩된 `if` 블록을 포함하는 `switch` 문 내에 위치해 있었습니다.

```c
// [RECONSTRUCTED] 제어 흐름 결함의 단순화된 표현
switch (message_type) {
    case IAM_MESSAGE:
        if (dln_status == UPDATING_MAP) {
            // 프로그래머는 'if' 블록을 빠져나가려고 의도했습니다.
            // 하지만 C 언어에서 'break'는 자신을 감싸는 'switch' 또는 'loop'를 빠져나갑니다.
            break; 
        }
        
        // 'break'가 실행되면 중요한 포인터 초기화를 건너뜁니다
        optional_params_ptr = initialize_params(message);
        
        // ...
        
    case OTHER_MESSAGE:
        // ...
}

// 이후의 코드는 포인터를 사용하지만, 'break' 경로를 탔을 경우
// 이 포인터는 현재 초기화되지 않은 상태입니다.
process_optional_parameters(optional_params_ptr);
```

C 언어에서 `break` 문은 가장 안쪽의 `switch`, `while`, `do`, 또는 `for` 문을 빠져나갑니다. `if` 블록을 빠져나가는 것이 **아닙니다**. 프로그래머는 아마도 특정 로직 블록을 건너뛰고 포인터 초기화로 진행하려고 했겠지만, 대신 전체 `switch` 구문을 빠져나가고 말았습니다.

이후 프로세서가 초기화되지 않은 포인터를 사용하여 선택적 매개변수를 처리하려고 시도했을 때, 프로세서의 데이터가 손상되었습니다. DLN의 자체 검사 메커니즘은 이 손상을 감지하고 해당 DLN을 서비스에서 제외한 뒤, 짝(mate) 프로세서로 제어권을 넘기려 시도했습니다. 하지만 들어오는 트래픽의 압박이 일정하게 유지되고 있었기 때문에, 짝 프로세서도 즉시 좁은 간격의 동일한 IAM들과 마주쳤고 동일한 결함을 겪었으며, 결국 전체 교환기가 스스로를 신호망으로부터 격리하여 복구를 시도하게 되었습니다.


## 피해 규모와 복구

9시간 동안 통신망은 지속적으로 연달아 일어나는 장애 상태에서 몸부림쳤습니다.

AT&T는 그날 1억 4,800만 통화가 처리되었으나 8,300만 통화만이 완료되어 56%의 통화 성공률을 기록했다고 발표했습니다. 당시 추산에 따르면 약 6,000만~7,500만 달러의 수익 손실이 발생했습니다. Los Angeles Times의 보도에 따르면 아메리칸 항공의 수신용 800번 통화량은 3분의 2가량 감소했지만, Sabre 예약 시스템은 별도의 전화선을 사용했기 때문에 정상적으로 가동되었습니다. 메리어트 호텔은 평소 통화량의 10% 수준만을 받았습니다.

### 3단계 복구 과정

1. **안정화 (Stabilize):** AT&T는 백업 링크의 신호 트래픽을 일시적으로 중단하여 영향을 받은 DLN 프로세서에 도달하는 메시지 부하를 줄임으로써 네트워크를 안정화시켰습니다. 오후 11시 30분경(EST) 정상 서비스가 재개되었습니다.
2. **억제 (Contain):** 다음 날, AT&T는 결함이 있는 프로그램 업데이트를 제거하고 이전 프로그램 버전으로 일시적으로 복귀했습니다.
3. **수정 (Correct):** 엔지니어들은 실험실에서 문제를 재현하고, 결함을 수정한 뒤 변경 사항을 테스트하고 백업 신호 링크를 복원했습니다.

## 시스템 예방 플레이북

프로덕션 환경에서의 장애는 복구-경로 테스트의 공백을 드러냈습니다. 실험실 테스트에서는 복구, 상태 맵 업데이트, 좁은 간격의 IAM들, 반복적인 피어 장애로 이어지는 이 특정한 시퀀스를 재현하지 못했던 것입니다.

### 1. 제한된 복구 권한 (Bounded Recovery Authority)
복구 메커니즘은 제한된 권한을 가져야 합니다. 피어의 복구 이벤트가 네트워크 전체에 걸쳐 무제한적인 일련의 로컬 복구 조치를 촉발시켜서는 안 됩니다. 속도 제한, 히스테리시스, 재시도 예산 및 에스컬레이션 임계값은 자동 복구가 피드백 증폭기로 변하는 것을 방지할 수 있습니다.

### 2. 정적 분석 및 도구 (Static Analysis and Tooling)
최신 컴파일러, 린터 및 정적 분석 도구는 수상한 제어 흐름과 잠재적으로 초기화되지 않은 상태의 여러 형태를 감지할 수 있습니다. 보다 강력한 컴파일러 진단과 구조화된 제어 흐름 검토는 이러한 종류의 결함이 검토를 빠져나갈 가능성을 줄여줍니다.

### 3. 다양성 대 동질성 (Diversity vs. Homogeneity)
AT&T 사건은 단일 문화(monoculture)의 위험성을 보여주었습니다. 동일한 취약점을 가진 소프트웨어 업데이트가 모든 노드에서 실행되고 있었습니다. 복구 트래픽이 추가 노드들에서 동일한 결함을 반복적으로 촉발시킬 수 있다면, 다수의 하드웨어(Redundancy)만으로는 함대 전체에 복제된 공통의 소프트웨어 결함을 방어할 수 없습니다.

## 과거와 현재: 엔지니어링의 진화

| 장애 관점 | 1990년의 장애 | 현대 엔지니어링 관행 |
| :--- | :--- | :--- |
| **배포 (Deployment)** | 114개 교환기에 업데이트 동시 푸시 | 카나리아 배포, 단계적 롤아웃, 폭발 반경 억제 |
| **복구 신호 (Recovery Signaling)** | 피어 복구가 로컬 상태의 취약점을 직접 촉발함 | 제한된 이벤트 전파, 속도 제한, 서킷 브레이커, 재시도 예산, 명시적인 복구-상태 기계 |
| **장애 격리 (Failure Isolation)** | 오류 복구 메커니즘이 전파 벡터로 작용함 | 제어 평면(Control Plane) 상태와 데이터 평면(Data Plane) 처리의 엄격한 분리 |
| **검증 (Verification)** | 코드 리뷰에서 감지되지 않은 C 제어 흐름의 모호성 | 자동화된 정적 분석, 린터(예: `-Wuninitialized`, `-Wimplicit-fallthrough`) |

## 증거가 입증하는 것:
> **[DOCUMENTED]**
> - 초기 트리거는 뉴욕의 트렁크 인터페이스 하드웨어 문제였습니다.
> - 취약한 소프트웨어는 백업 신호망 접근성을 개선하기 위해 12월 중순 업데이트에 도입되었습니다.
> - 수신 측 DLN이 상태 맵을 업데이트하는 동안 1/100초 이내에 도착한 두 개의 간격이 좁은 IAM이 장애의 필수 조건이었습니다.
> - 통화 성공률은 56%로 떨어졌습니다 (처리된 1억 4,800만 통화 중 8,300만 통화 완료).
> - AT&T는 백업 링크의 신호 트래픽을 일시적으로 중단시켜 네트워크를 안정화했습니다.

## 증거가 입증하지 않는 것 (What the evidence does NOT establish):
> **[UNKNOWN BOUNDARIES]**
> - 정확한 내부 변수 이름, 메모리 주소, 프로세서 명령어 및 완전한 프로덕션 소스 코드는 공개된 1차 자료에서 여전히 밝혀지지 않았습니다.
> - 사이버 공격, 악의적 의도 또는 외부 침입에 대한 어떠한 증거도 없습니다.

> **아키비스트의 분석:**
> 이 장애는 단순히 잘못된 `break` 문의 문제가 아니었습니다. `break`는 로컬 결함을 만들었고, 4ESS 함대 전체에 걸쳐 동일한 취약한 복구 소프트웨어가 배포되면서 공통 모드(common-mode) 조건이 형성되었으며, 자동 복구는 반복적인 트리거를 만들었고, CCS7 신호는 전파 경로를 제공했습니다.
> 
> 초기의 하드웨어 오류는 일상적인 것이었습니다. 대재앙은 시스템의 복구 경로가 이웃 노드의 동일한 소프트웨어 결함과 결합되면서 발생했습니다. 즉, 서비스를 복원하도록 설계된 메커니즘이 역설적으로 새로운 장애를 반복해서 만들어내는 메커니즘이 된 것입니다.
> 
> 이것이 바로 1990년 AT&T 통신망 마비 사태가 남긴 지속적인 교훈입니다. 시스템의 신뢰성은 구성 요소가 장애를 견뎌낼 수 있는지만을 질문하여 평가할 수 없습니다. 회복력 있는 시스템이라면 구성 요소가 복구되고, 그 복구를 알리며, 다른 구성 요소들이 동시에 상태를 변경하고 있는 네트워크에 재진입할 때 어떤 일이 발생하는지에 대해서도 반드시 테스트되어야 합니다.
