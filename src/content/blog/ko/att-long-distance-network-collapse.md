> **증거가 입증하는 것:**
> - 코드에는 `switch` 문 내의 `if` 블록 안에 잘못 배치된 `break` 문이 포함되어 있었습니다.
> - 네트워크 마비는 114개 교환기에 걸친 빠르고 동일한 자동 복구 응답으로 인해 발생했습니다.
> - 이 중단으로 인해 9시간 동안 네트워크 용량의 약 50%가 차단되었습니다.

## AT&T 4ESS 네트워크란 무엇이었나?

1990년까지 AT&T는 미국 통신 인프라의 백본을 운영하고 있었습니다. 이 네트워크의 핵심에는 114개의 **4ESS(Number 4 Electronic Switching System)** 장거리 교환기가 있었습니다. 이 거대하고 신뢰성이 높은 컴퓨터들은 전국적으로 장거리 통화를 라우팅했습니다.

이러한 교환기들은 효율적인 통신을 위해 **SS7 (Signaling System No. 7)** 프로토콜을 사용했습니다. 음성 회선을 통해 라우팅 정보를 보내는 대신, SS7은 전용 데이터 네트워크를 사용하여 통화 설정, 종료 및 상태 업데이트를 조정했습니다. 이러한 대역 외 신호 처리는 네트워크를 놀라울 정도로 빠르게 만들었지만, 동시에 전국의 모든 주요 교환기 간에 긴밀한 논리적 결합을 생성했습니다.

## 제1막: 속도를 향한 추구

1989년 12월 중순, AT&T는 114개의 4ESS 교환기 전체에 소프트웨어 업데이트를 배포했습니다. 이 업데이트는 교환기가 인접 장비의 상태 메시지를 처리하는 방식을 간소화하여 장거리 연결 설정에 필요한 시간을 줄이도록 설계되었습니다.

코드는 시스템 프로그래밍의 업계 표준인 C 언어로 작성되었습니다. 특정 루틴은 교환기가 인접 교환기로부터 "서비스 불가(Out of Service)" 메시지를 받은 후 즉시 "서비스 중(In Service)"(또는 복구) 메시지를 받았을 때 교환기가 어떻게 반응할지를 제어했습니다.

몇 주 동안 업데이트된 소프트웨어는 완벽하게 작동했습니다. 근본적인 결함을 유발하는 데 필요한 특정한 타이밍 조건이 실제 환경에서는 아직 발생하지 않았기 때문입니다.

## 제2막: 누락된 Break의 해부

> **재구성된 장애 모델:** 내부 구현 세부 정보가 부분적으로 공개되지 않음.
> 취약점은 C 프로그래밍 언어 구문의 기본적인 특성에 있었습니다. 개발자들은 들어오는 다양한 유형의 메시지를 처리하기 위해 `switch` 문을 작성했습니다. `case` 블록 중 하나 내부에 그들은 특정 엣지 조건(Edge Condition)을 처리하기 위해 `if` 문을 포함시켰습니다.

```c
switch (message_type) {
    // ... 다른 경우들 ...
    case IN_SERVICE_MESSAGE:
        if (optional_parameters_present) {
            // 일부 설정 수행
            if (condition_met) {
                // IF 블록을 빠져나갈 의도로 작성됨
                break; 
            }
            // 선택적 작업을 위한 포인터 초기화
            initialize_pointers();
        }
        // ... 포인터를 사용하여 선택적 작업 실행 ...
        break;
}
```

> **추론:** 개발자는 `if (condition_met)` 블록 내부의 `break` 문이 단순히 `if` 절을 빠져나와 `case` 블록의 나머지 부분으로 진행하도록 의도했습니다. 그러나 C 언어에서 `break`는 항상 가장 가까운 루프나 `switch` 문을 종료합니다.

빠른 연속적인 메시지가 교환기에 도달했을 때 해당 조건이 충족되었습니다. `break`가 실행되어 프로그램이 `switch` 블록 전체에서 빠져나왔습니다. 필수적인 `initialize_pointers()` 함수는 건너뛰어졌지만, 후속 코드는 메모리의 초기화되지 않은 가비지 데이터를 사용하여 "선택적 매개변수 작업"을 여전히 실행하려고 시도했습니다.

## 제3막: 연쇄 장애 시퀀스

1990년 1월 15일 월요일 오후 2시 25분(EST), 뉴욕시의 4ESS 교환기 한 대가 사소하고 일상적인 하드웨어 이상을 겪었습니다. 설계된 대로 정확하게 작동하여, 일시적으로 자신을 서비스에서 제외하고 자체 진단을 실행한 후 자신을 재설정했습니다.

1. **촉매제:** 뉴욕 교환기는 네트워크에 "서비스 불가" 메시지를 브로드캐스트했고, 성공적으로 복구된 후 밀리초 단위로 "서비스 중" 메시지를 보냈습니다.
2. **감염:** 인접 교환기가 이 빠른 메시지 쌍을 수신했습니다. 이것이 C 코드의 정확한 엣지 조건을 트리거했습니다. `break` 문이 실행되고 포인터 초기화가 생략되었으며 교환기는 잘못된 메모리 주소에 기록을 시도했습니다.
3. **자체 방어의 함정:** 메모리 손상을 감지한 두 번째 교환기의 내부 결함 허용(Fault-tolerance) 루틴은 스스로를 보호하기 위해 즉각적인 자체 재부팅을 트리거했습니다.
4. **전파:** 두 번째 교환기가 재설정되면서 *그것은* 다시 자신의 "서비스 불가" 및 "서비스 중" 메시지를 피어들에게 브로드캐스트했습니다. 피어들은 그 빠른 메시지를 수신하고, 동일한 소프트웨어 버그에 부딪혀 즉시 자신들을 재설정했습니다.

불과 몇 분 만에 버그는 대륙 전체로 퍼져나갔습니다. 114개의 교환기가 상태 업데이트로 서로를 의도치 않게 감염시키면서 계속해서 다운되고, 재부팅되고, 다시 다운되었습니다. 복원력을 위해 설계된 SS7 네트워크가 소프트웨어 전염병의 고속 매개체가 되어버렸습니다.

## 제4막: 재정 및 법적 파장 표

마틴 루터 킹 주니어 기념일 휴일이라는 통화량이 많은 날에 발생한 이 붕괴 사태는 미국 통신망을 마비시켰습니다.

| 주체 | 운영상 영향 | 재무/평판 결과 |
| :--- | :--- | :--- |
| **AT&T** | 9시간 동안의 전국적인 네트워크 마비; 용량 50% 감소. | 약 6천만 달러의 장거리 통화 수익 손실 추정; 막대한 평판 손상. |
| **아메리칸 항공** | 세이버(Sabre) 예약 시스템 연결 단절. | 약 200,000건의 예약 손실 추정. |
| **일반 대중** | 6천만 건의 통화 차단; 응급 서비스 중단. | 디지털 통신 인프라에 대한 심각한 신뢰 상실. |

이 주기를 끊기 위해 AT&T 엔지니어들은 교환기들이 서로에게 빠른 상태 업데이트를 압도하지 않고 안정화될 수 있을 때까지 SS7 메시지를 사실상 조절(Throttling)하여 네트워크의 신호 부하를 체계적으로 줄여야 했습니다. 밤 11시 30분이 되어서야 네트워크가 마침내 복구되었습니다.

## 테스트에서 발견하지 못한 이유

AT&T 네트워크는 지구상에서 가장 엄격한 테스트 프로토콜의 대상이었습니다. 왜 단순한 `break` 문 하나가 그것을 무너뜨렸을까요?

1. **환경적 동질성:** 테스트를 통해 소프트웨어가 개별 교환기와 작고 통제된 클러스터에서 완벽하게 작동함이 확인되었습니다. 그러나 교환기가 복구되면서 특정 처리 주기를 겪고 있는 피어에게 상태 업데이트를 쏘아 보내는 정확한 타이밍 메커니즘은 전국적인 규모에서만 나타나는 매우 발생 확률이 낮은 경쟁 조건(Race condition)이었습니다.
2. **이중화의 역설:** AT&T의 네트워크는 고도로 이중화되어 있었지만 *논리적으로는 동질적*이었습니다. 모든 교환기가 정확히 동일한 버전의 소프트웨어를 실행했습니다. 이중화된 하드웨어는 모든 노드에서 동시에 트리거되는 결정론적인 소프트웨어 버그로부터 보호할 수 없습니다.
3. **테스트는 전염을 모델링하지 않았다:** 시뮬레이션 환경은 교환기 장애(노드 다운)를 테스트했지만, 건강한 노드에 파괴적인 힘으로 작용하는 *복구 메시지 자체의 동작*은 적절하게 모델링하지 않았습니다.

## 시스템 예방 플레이북

현대의 분산 시스템은 AT&T 붕괴에서 얻은 교훈에 크게 의존하고 있습니다. 엔지니어링 팀은 세 가지 별개의 클래스에 걸쳐 방어 구조를 구현해야 합니다.

### 1. 마찰 방어 (Friction Defenses: 운영자 및 배포 제어)
* **카나리아 배포 (Canary Deployments):** 동질적인 네트워크의 100%에 중요한 업데이트를 동시에 배포해서는 안 됩니다. 업데이트는 작고 통계적으로 유의미한 클러스터(카나리아)에 롤아웃되어 더 광범위하게 릴리스되기 전에 며칠 동안 구워져야(baking) 합니다.
* **엇갈린 버전 관리 (Staggered Versioning):** 이기종 소프트웨어 환경을 유지(예: 플릿의 절반에서는 버전 N을, 나머지 절반에서는 N-1을 실행)하면 단일 논리적 버그가 전체 네트워크를 붕괴시키는 것을 방지할 수 있습니다.

### 2. 경계 제약 (Boundary Constraints: 물리적 및 논리적 불변성)
* **정적 코드 분석 (Static Code Analysis):** 최신 컴파일러(GCC 또는 Clang 등)와 린터는 1990년의 C 컴파일러가 묵인했던 의심스러운 `break` 폴스루(fall-throughs) 또는 초기화되지 않은 포인터 사용을 일상적으로 경고합니다.
* **서킷 브레이커 (Circuit Breakers):** 시스템은 상태 변경 빈도를 추적해야 합니다. 피어가 플래핑(빠르게 연결 및 연결 해제)하는 경우, 네트워크는 맹목적으로 해당 상태 업데이트를 처리하는 대신 해당 노드를 논리적으로 격리해야 합니다.

### 3. 비상 브레이크 (Emergency Brakes: 최종 상태 정지)
* **컨트롤 플레인 분리:** 컨트롤 플레인(SS7)이 오류 메시지로 포화 상태가 되었을 때, 데이터 플레인 라우팅 하드웨어에서 커널 수준의 패닉이나 하드 재설정을 유도할 수 있는 기능을 보유해서는 안 됩니다.

## FAQ

### 1990년 AT&T 통신 마비 사태의 정확한 원인은 무엇입니까?
1989년 12월 중순 업데이트에서 도입된 소프트웨어 버그입니다. C 프로그램 내에 잘못 배치된 `break` 문으로 인해 인접 교환기로부터 특정한 빠른 상태 메시지 시퀀스를 수신했을 때 교환기가 자체 메모리를 손상시켰습니다.

### 어떻게 단 하나의 버그가 국가 전체의 통신망을 마비시킬 수 있었습니까?
네트워크가 논리적으로 동질적이었습니다. 모든 교환기가 정확히 동일한 소프트웨어를 실행했습니다. 한 교환기가 충돌하고 재부팅될 때, 그 복구 메시지가 이웃 교환기들의 버그를 트리거하여 그들 역시 충돌하고 자신의 복구 메시지를 보내게 만듦으로써 연쇄적인 도미노 효과를 일으켰습니다.

### 해커가 AT&T 붕괴를 일으킨 것입니까?
아닙니다. 초기에는 사이버 공격이나 컴퓨터 바이러스에 대한 소문이 널리 퍼졌지만, AT&T의 법의학적 조사를 통해 그것이 내부 코딩 오류였음이 결정적으로 입증되었습니다.

### AT&T 네트워크는 얼마나 오래 중단되었습니까?
심각한 통신 장애는 1990년 1월 15일에 약 9시간 동안 지속되었으며, 미국 내 국내 장거리 통화의 약 50%가 차단되었습니다.

### 1990년 통신 마비로 인해 AT&T는 얼마나 많은 비용을 치렀습니까?
AT&T는 신뢰성에 대한 돌이킬 수 없는 평판 손상과 함께 직접적인 장거리 통화 수익에서 약 6천만 달러를 잃은 것으로 추정됩니다.

### 버그는 어떤 프로그래밍 언어로 작성되었습니까?
버그는 C 언어로 작성되었습니다. 개발자는 `switch` 문 내부에 중첩된 `if` 문 안에 배치될 때 `break` 문이 어떻게 동작하는지 오해했습니다.

### AT&T는 네트워크 붕괴를 어떻게 해결했습니까?
엔지니어들은 네트워크의 신호 부하를 일시적으로 줄여 SS7 메시지를 사실상 조절(throttling)했습니다. 이를 통해 교환기들이 빠른 상태 업데이트로 서로를 즉시 압도하지 않고 안정화 및 재부팅될 수 있었습니다. 이후 결함이 있는 소프트웨어가 패치되었습니다.

### AT&T의 1990년 충돌이 현대 소프트웨어에서 중요한 이유는 무엇입니까?
그것은 연쇄 장애의 교과서적인 예입니다. 이는 기술 산업이 테스트 프로토콜을 다시 생각하게 만들었으며, 동질적 인프라의 위험성을 강조하고 자동화된 결함 허용(fault-tolerance) 시스템이 때로는 파국적 장애의 매개체로 작용할 수 있음을 증명했습니다.
