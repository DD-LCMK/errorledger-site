## 사건 개요 및 포렌식 요약

1985년 6월부터 1987년 1월 사이, 캐나다 원자력공사(AECL)가 제조한 의료용 선형 가속기 **테락-25(Therac-25)**가 미국과 캐나다의 4개 병원에서 최소 6명의 암 환자에게 치명적인 방사선 과피폭을 가했습니다. 테락-25는 임베디드 컴퓨터 제어를 도입하여 치료 절차를 혁신적으로 단순화한 최첨단 방사선 치료 장비로 대대적으로 마케팅되었습니다.

그러나 이 장비는 안전 필수 소프트웨어 역사상 가장 비극적인 참사의 대명사가 되었습니다.

이전 세대 모델인 테락-6와 테락-20에서는 텅스텐 타깃과 빔 평탄화 필터가 빔 경로에 완벽히 정렬되지 않으면 물리적으로 전자기 빔이 발사되지 못하도록 막는 **전기기계식 하드웨어 인터록(릴레이 및 마이크로스위치)**이 장착되어 있었습니다. 하지만 테락-25를 설계하면서 AECL 엔지니어들은 "소프트웨어가 충분히 신뢰할 수 있으므로 하드웨어 안전 인터록은 불필요하다"는 위험한 가정을 내리고 모든 물리적 안전 회로를 제거했습니다.

단 한 명의 프로그래머가 작성하고 독립적인 코드 리뷰조차 거치지 않은 PDP-11 어셈블리 제어 소프트웨어에는 치명적인 **동시성 레이스 컨디션(Race Condition)**과 **정수 오버플로 결함**이 도사리고 있었습니다. 숙련된 치료사가 키보드 입력을 빠르게 수정하면, 장비의 회전판(턴테이블)이 보호 위치로 이동하지 않은 상태에서 전자총이 25 MeV 고출력 X선 모드로 발사되었습니다. 환자들은 아무런 감쇠 타깃이나 산란판 없이 25,000 라드(치사량의 100배 이상)에 달하는 순수 고에너지 전자선에 직접 타격을 입어 심각한 조직 괴사와 장기 파괴로 목숨을 잃었습니다.

## 1막: 아키텍처의 배신 — 릴레이 회로를 어셈블리어로 대체하다

의료용 선형 가속기는 환자의 암 세포를 파괴하기 위해 두 가지 근본적으로 다른 모드로 작동합니다:

1. **직접 전자선 치료(Direct Electron Mode):** 얕은 피부암 치료에 사용됩니다. 수 나노암페어 수준의 매우 낮은 빔 전류를 사용하여 저에너지 전자선을 환자 환부에 직접 조사하며, 산란 자석을 통해 방사선을 넓게 분산시킵니다.
2. **X선 광자 치료(X-Ray Photon Mode):** 체내 깊숙이 위치한 종양을 치료합니다. 전자총에서 전자선 모드보다 **100배에서 1,000배 높은 고전류 25 MeV 전자 빔**을 발사하여 무거운 텅스텐-탄탈륨 타깃에 충돌시킵니다. 전자가 금속에 부딪힐 때 발생하는 제동 복사(Bremsstrahlung) X선과 빔 평탄화 필터를 통과시켜 인체에 안전한 치료용 방사선으로 변환합니다.

이전 세대 모델인 테락-6와 테락-20에서는 안전이 **전기기계식 릴레이 하드웨어**에 의해 보장되었습니다. 텅스텐 타깃이 빔 출구 정면에 물리적으로 맞물려 스위치를 누르지 않는 한, 전자총 전원 회로가 차단되어 고전류 빔을 발사하는 것이 물리적으로 불가능했습니다.

```text
[테락-20 안전 구조]
소프트웨어 제어 ───▶ [물리적 하드웨어 인터록 릴레이] ───▶ 안전한 빔 발사
                               ▲
                      (물리적 타깃 위치 센서)

[테락-25 위험 구조]
소프트웨어 제어 ─────────────────────────────────────────▶ 무방비 빔 발사!
                      (하드웨어 인터록 전면 제거)
```

AECL 경영진과 엔지니어링 팀은 테락-25를 설계하면서 치명적인 결정을 내렸습니다. 제조 비용을 절감하고, 기기 무게를 줄이며, "완전한 디지털 컴퓨터 제어"라는 세련된 마케팅 문구를 내세우기 위해 물리적 인터록 회로를 전면 제거했습니다. 기계의 생명 안전 제어 전체가 DEC PDP-11 미니컴퓨터에서 실행되는 실시간 어셈블리 코드에 전적으로 맡겨졌습니다.

더욱 심각한 것은 소프트웨어를 처음부터 정밀 검증하며 작성한 것이 아니라, 1970년대 초 테락-6/20용으로 작성되었던 오래된 어셈블리 코드를 그대로 재사용했다는 점입니다. 이전 기계들에서는 하드웨어 인터록이 조용히 소프트웨어의 동시성 버그를 막아주고 있었기 때문에, 코드 내부의 치명적인 결함은 10년 동안 발견되지 않은 채 시한폭탄처럼 숨어 있었습니다.

## 2막: 8초 편집 함정과 1바이트 카운터 오버플로

워싱턴 대학교의 낸시 레브슨(Nancy Leveson) 교수와 클라크 터너(Clark Turner)의 조사에 따르면, 테락-25에는 최소 두 개의 서로 다른 독립적인 소프트웨어 레이스 컨디션 결함이 존재했습니다.

### 1. 텍사스 타일러 병원 사건: 8초 키보드 편집 레이스 컨디션 (Malfunction 54)

1986년 3월 21일, 텍사스주 타일러에 위치한 이스트 텍사스 암 센터에서 숙련된 방사선 치료 기사 레이 콕스(Ray Cox)는 어깨 종양 환자 레이 잉그램(Ray Ingram)을 치료하기 위해 콘솔 앞에 앉았습니다.

키보드 타이핑에 매우 능숙했던 콕스는 콘솔에 다음과 같은 순서로 빠르게 입력했습니다:
1. 실수로 광자 모드를 의미하는 `X`를 입력했습니다.
2. 처방이 전자선 모드임을 깨닫고 즉시 `Up-Arrow` 키를 눌러 모드 선택 필드로 돌아간 뒤 `E`를 입력했습니다.
3. 기본 파라미터를 확정하기 위해 `Enter` 키를 연타하여 설정을 마쳤습니다.
4. 이 모든 키 입력 수정 과정은 **8초 이내**에 완료되었습니다.

```text
┌──────────────────────────────────────────────────────────────────────────────────────┐
│                        8초 키보드 편집 레이스 컨디션의 메커니즘                       │
├──────────────────────────────────────────────────────────────────────────────────────┤
│ 1. 치료사가 'X'(광자 모드) 입력                                                      │
│    └─► 서브루틴 'HBI'가 턴테이블 텅스텐 타깃 이동 시작 (물리적으로 약 8초 소요)      │
│                                                                                      │
│ 2. 치료사가 8초 이내에 Up-Arrow를 누르고 'E'(전자 모드)로 변경 후 Enter 확정        │
│    └─► 소프트웨어는 파라미터 입력 완료 플래그를 설정함.                              │
│    └─► 자석 설정은 재설정되었으나, 턴테이블 이동 명령은 취소/동결됨.                 │
│                                                                                      │
│ 3. 기계 상태의 치명적 불일치:                                                        │
│    ├─ 빔 전류 출력: X선용 최고 출력 모드 유지 (전자선 대비 100배 고전류)             │
│    └─ 턴테이블 물리 위치: 필드 라이트 위치 (텅스텐 타깃 없음, 평탄화 필터 없음)     │
│                                                                                      │
│ 4. 결과: 25,000 라드의 비감쇠 고출력 전자선이 0.04초 만에 환자의 몸을 관통함         │
└──────────────────────────────────────────────────────────────────────────────────────┘
```

PDP-11 어셈블리 코드의 서브루틴 `HBI`(Handle Beam Initialization)는 `X`가 입력되면 턴테이블을 회전시켜 무거운 텅스텐 타깃을 빔 출구에 배치하도록 명령했습니다. 이 기계적 회전에는 약 8초가 걸렸습니다.

치료사가 8초 이내에 모드를 `E`로 수정하자, 상위 레벨의 모드 변수는 전자선으로 변경되었지만 턴테이블 위치를 확인하고 재배치하는 서브루틴은 실행되지 않았습니다. 반면 가속기 제어 장치는 고출력 25 MeV X선 발생을 위한 최대 전류 출력 상태를 유지했습니다.

콕스가 `B`(Beam On) 버튼을 누르는 순간, 선형 가속기는 **텅스텐 타깃이나 산란 필터가 전혀 없는 상태에서 25 MeV 초고출력 전자선**을 레이 잉그램의 등에 그대로 쏟아부었습니다.

잉그램은 등 뒤에서 불타는 쇠꼬챙이로 찔리는 듯한 충격과 굉음을 느꼈습니다. 콘솔 모니터에는 `Malfunction 54`라는 오류와 함께 `조사량 부족(Dose Under)`이라는 상태가 떴습니다. 콕스는 방사선이 전혀 조사되지 않았다고 판단하고 `P`(Proceed) 키를 눌러 치료를 재개했습니다. 잉그램은 2차 과피폭을 당해 총 30,000 라드 이상의 방사선을 흡수했고, 극심한 척수 괴사와 장기 손상으로 5개월 뒤 사망했습니다.

### 2. 워싱턴 야키마 사건: 1바이트 카운터 오버플로 (Malfunction 13)

1987년 1월 워싱턴주 야키마 밸리 기념병원에서 발생한 또 다른 치명적 사고는 `Set-Up Test` 루틴의 1바이트 카운터 변수에서 비롯되었습니다.

소프트웨어는 편향 자석의 위치가 올바른지 검사하는 루틴에서 `Class3`이라는 8비트(1바이트) 공유 변수를 사용했습니다. 검사 루프를 돌 때마다 이 변수는 1씩 증가했습니다:

```text
어셈블리 제어 로직:
  INC Class3       ; 8비트 카운터 증가 (0 ~ 255)
  BNE MagnetCheck  ; Class3이 0이 아니면 자석 위치 검사 계속 수행
  JSR FireBeam     ; Class3이 0이면 검사를 생략하고 즉시 빔 발사 허용!
```

`Class3` 변수는 부호 없는 8비트 정수였기 때문에 255를 초과하면 **0으로 롤오버(0으로 리셋)**되었습니다. 조작자가 마침 `Class3` 변수가 0이 되는 바로 그 밀리초에 `Set` 버튼을 누르면, 소프트웨어는 자석 위치 검사를 아예 건너뛰고 "모든 안전 검사가 완료되었다"고 오판하여 빔을 발사했습니다.

이로 인해 자석이 제대로 정렬되지 않은 상태에서 집중된 전자선 빔이 환자의 가슴을 관통하여 심각한 방사선 화상을 입혔고, 환자는 몇 달 뒤 사망했습니다.

## 3막: 침묵하는 경보 — Malfunction 54와 운영자 인터페이스의 덫

테락-25의 UI/UX 설계는 공학적 실패를 임상적 비극으로 증폭시키는 촉매제 역할을 했습니다.

VT100 콘솔 화면에는 `Malfunction 1`부터 `Malfunction 64`까지 수십 가지의 오류 코드가 표시되었지만, 병원에 제공된 운영 매뉴얼 어디에도 이 번호들이 무엇을 의미하는지 설명하는 부록이 없었습니다.

```text
┌──────────────────────────────────────────────────────────────────────────────────────┐
│                    DEC VT100 운영자 콘솔 실제 인터랙션 기록                           │
├──────────────────────────────────────────────────────────────────────────────────────┤
│ OP> COMMAND: X-RAY 25 MEV                                                            │
│ OP> EDIT: UP-ARROW -> ELECTRON MODE -> ENTER                                         │
│ CONSOLE> READY FOR BEAM DELIVERY                                                     │
│ OP> B [ENTER]                                                                        │
│ TELEMETRY> BEAM PULSE FIRED: 0.04 SECONDS                                            │
│ ALARM> MALFUNCTION 54                                                                │
│ STATUS> DOSE DELIVERED: 0.00 RADS                                                    │
│ STATUS> TREATMENT PAUSED - PRESS 'P' TO PROCEED OR 'C' TO CANCEL                     │
│                                                                                      │
│ OP> P [ENTER]  (경보 피로로 인한 기계적 재시도)                                      │
│ TELEMETRY> SECOND BEAM PULSE FIRED: 0.04 SECONDS                                     │
│ ALARM> MALFUNCTION 54                                                                │
└──────────────────────────────────────────────────────────────────────────────────────┘
```

`Malfunction 54`나 `Malfunction 13`이 발생했을 때 기계는 사이렌을 울리거나 장비를 비상 락다운하지 않았습니다. 대신 화면에 `TREATMENT PAUSE`를 띄우며 조사량이 0에 가깝다고 보고했습니다.

무엇보다 소프트웨어는 기사가 단순히 `P` 키를 누르기만 하면 경보를 해제하고 즉시 빔을 재발사할 수 있도록 허용했습니다. 일상적인 캘리브레이션 과정에서 사소한 에러가 하루에도 수십 번씩 발생했기 때문에, 치료사들에게 `P` 키를 눌러 진행하는 것은 무조건적인 **반사적 습관(경보 피로, Alert Fatigue)**이 되어 있었습니다.

## 4막: 조직적 부인, FDA의 강제 리콜, 그리고 법적 책임

캐나다 원자력공사(AECL)의 조직적 대응은 공학적 오만과 기업의 책임 회피를 여실히 보여줍니다:

1. **물리적 불가능성 주장 (1985년 6월 ~ 1986년 1월):** 조지아주와 텍사스주의 병원에서 극심한 화상 피해가 보고되었을 때, AECL 엔지니어들은 간단한 테스트 후 버그를 재현하지 못하자 "소프트웨어 보호 장치가 다중으로 되어 있어 과피폭은 물리적으로 불가능하다"며 공식 서한을 보내 병원 측 주장을 묵살했습니다.
2. **병원 측 과실 전가 (1986년 3월):** AECL은 병원의 접지 불량, 정전기, 또는 치료 기사의 미숙한 조작 탓으로 책임을 돌렸습니다.
3. **FDA 클래스 1 리콜 발동 (1987년 2월):** 이스트 텍사스 암 센터의 물리학자 프리츠 헤이거(Fritz Hager)가 키보드 입력 타이밍을 역공학하여 버그를 완벽히 재현해 낸 후에야 AECL은 결함을 시인했습니다. 미국 FDA는 1987년 2월 10일 테락-25에 대해 사망 위험이 있는 최고 등급인 **클래스 I 강제 리콜**을 발령하고, 물리적 하드웨어 인터록이 장착될 때까지 북미 전역의 기기 사용을 전면 금지했습니다.

## 시스템 예방 플레이북: 현대 안전 엔지니어링 방어선

테락-25 참사의 교훈은 현대 의료 기기 소프트웨어 표준(IEC 62304)과 항공우주, 원자력 등 안전 필수 시스템의 핵심 아키텍처 원칙이 되었습니다.

```text
┌────────────────────────────────────────────────────────────────────────────────────────┐
│                         안전 필수 시스템을 위한 3대 방어 클래스                        │
├────────────────────────────────────────────────────────────────────────────────────────┤
│ 1. 마찰 방어 (Friction Defenses)                                                        │
│    [역사적 교훈]: 빠른 UI 수정이 비동기 하드웨어 물리 상태와 충돌함.                   │
│    [현대 엔지니어링]: 하위 I/O가 진행 중일 때 상태 전이를 차단하는 트랜잭션 격리 보장. │
│                                                                                        │
│ 2. 경계 제약 (Boundary Constraints)                                                    │
│    [역사적 교훈]: 8비트 정수 카운터가 오버플로되어 0이 되는 결함 방치.                 │
│    [현대 엔지니어링]: 컴파일 타임 정적 범위 검사 및 정수 롤오버 시 강제 패닉(Fail-Safe).│
│                                                                                        │
│ 3. 비상 제동 (Emergency Brakes)                                                        │
│    [역사적 교훈]: 소프트웨어를 맹신하여 물리적 하드웨어 인터록을 제거함.                │
│    [현대 엔지니어링]: 소프트웨어와 완전히 독립된 아날로그 하드웨어 워치독 및 릴레이 차단.│
└────────────────────────────────────────────────────────────────────────────────────────┘
```

### 1. 마찰 방어 (Friction Defenses): UI 상태 트랜잭션 원자성
* **[역사적 교훈]:** 테락-25에서는 하위 기계 장치가 물리적으로 이동하는 동안 조작자가 UI 파라미터를 수정할 수 있었고, 이로 인해 소프트웨어 내부 상태와 물리 장비의 상태가 분리되는 참사가 일어났습니다.
* **[현대 엔지니어링 적용]:** 엄격한 상태 머신 트랜잭션 격리를 구현해야 합니다. 파라미터가 수정되면 즉시 모든 하위 액추에이터 실행 파이프라인을 원자적으로 취소하고 전체 유효성 검증을 처음부터 다시 통과하도록 강제해야 합니다.

### 2. 경계 제약 (Boundary Constraints): 산술 불변식 및 안전한 타입
* **[역사적 교훈]:** `Class3` 변수가 255를 넘어 0이 되면서 치명적인 안전 검사 무력화가 발생했습니다.
* **[현대 엔지니어링 적용]:** 정수 오버플로를 감지하면 자동으로 패닉하거나 안전 정지(Fail-Closed)하는 메모리 안전 언어(Rust 등)를 사용해야 합니다. 단순 스칼라 카운터를 안전 플래그로 전용해서는 안 되며, 명시적인 불리언 토큰과 상태 가드를 사용해야 합니다.

### 3. 비상 제동 (Emergency Brakes): 하드웨어 불변식 원칙
* **[역사적 교훈]:** 인명에 직접적인 위해를 가할 수 있는 시스템에서 소프트웨어가 단일 실패점(Single Point of Failure)이 되어서는 안 됩니다.
* **[현대 엔지니어링 적용]:** 모든 안전 필수 사이버-물리 시스템(의료 기기, 자율주행, 산업용 로봇)에서 생명 안전 경계는 소프트웨어 제어와 완전히 독립된 **아날로그 하드웨어 인터록(워치독 타이머, 기계식 리밋 스위치, 물리적 비상 차단기)**에 의해 이중으로 보호되어야 합니다.

## 아키비스트의 판결

> **아키비스트의 분석:** 테락-25 참사는 단순한 "프로그래밍 버그"의 사례로 자주 인용되지만, 이러한 진단은 근본적인 시스템 실패를 간과한 것입니다. 이 비극은 단순한 오타 때문에 발생한 것이 아니라 **시스템 아키텍처의 오만** 때문에 발생했습니다.
>
> AECL 엔지니어들은 시스템 공학에서 가장 위험한 착각에 빠졌습니다. 즉, 이전 모델에서 소프트웨어 사고가 관찰되지 않았다는 사실을 '소프트웨어가 안전하다는 증거'로 착각한 것입니다. 그들은 지난 10년 동안 환자들을 지켜주었던 것이 불완전한 소프트웨어가 아니라 묵묵히 버텨준 물리적 하드웨어 인터록이었다는 사실을 망각했습니다. 제조 단가를 낮추기 위해 물리적 안전장치를 제거하고 검증되지 않은 소프트웨어에 맹목적인 믿음을 바치는 행위는 혁신이 아닙니다. 그것은 엔지니어링의 위험을 무고한 인간의 육체로 외주화하는 무책임한 도박일 뿐입니다.
